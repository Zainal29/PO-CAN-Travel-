Lanjutkan dari hasil audit read-only terakhir.

Status audit saat ini adalah NEED FIX. Sekarang lakukan PERBAIKAN kode berdasarkan temuan audit tersebut.

ATURAN UTAMA:

1. Jangan mengubah scope di luar sistem order/payment.
2. Jangan membuat payment gateway eksternal.
3. Payment tetap simulasi internal.
4. Jangan menghapus data legacy secara destruktif.
5. Pertahankan DB::transaction(), locking, seats_released, dan e-ticket yang sudah berjalan.
6. Setelah setiap perubahan, periksa dampaknya terhadap test yang sudah ada.
7. Jangan menganggap FormRequest sebagai satu-satunya pengaman; business rule wajib divalidasi di service.
8. Jangan menambahkan status baru kecuali benar-benar diperlukan.

KONTRAK STATUS FINAL:

ORDER:
pending → paid
pending → cancelled
pending → expired
paid → completed

Tidak boleh:
pending → confirmed
confirmed → cancelled
paid → cancelled
paid → expired
cancelled → paid
expired → paid
completed → paid
completed → cancelled
completed → expired

PAYMENT:
unpaid → verified
unpaid → rejected
rejected → verified

Jika status pending payment digunakan:
pending → verified
pending → rejected

SOURCE OF TRUTH:
payments.status adalah satu-satunya source of truth payment.

orders.payment_status hanya legacy/derived compatibility dan tidak boleh digunakan sebagai sumber keputusan business logic.

PERBAIKAN WAJIB:

1. HAPUS/NONAKTIFKAN CONFIRMED

Cari seluruh penggunaan:

* confirmed
* pending → confirmed
* confirmed → cancelled
* filter order_status confirmed
* validasi confirmed sebagai active order
* tombol/aksi konfirmasi admin
* test yang menganggap confirmed sebagai status aktif

Sesuaikan dengan kontrak status baru.

Jangan sekadar menghapus string jika menyebabkan route/controller/test rusak. Periksa alurnya secara menyeluruh.

2. CANCELLATION

OrderCancellationService hanya boleh membatalkan order yang masih pending.

Aturan:
pending + unpaid → cancelled + rejected
pending + rejected → cancelled + rejected

Jika:
paid → tolak
completed → tolak
cancelled → tolak
expired → tolak
confirmed → tolak/tidak lagi didukung

Pastikan kursi dikembalikan tepat satu kali.

Pastikan cancel berulang tidak menggandakan available_seats.

3. EXPIRATION

Expiration hanya berlaku untuk pending order yang expired_at <= now().

Hasil:
pending + unpaid → expired + rejected
pending + rejected → expired + rejected

Order paid/completed/cancelled tidak boleh berubah menjadi expired.

Pastikan seats hanya dikembalikan satu kali.

4. PAYMENT SERVICE

PaymentService harus menjadi business-rule guard utama.

Validasi di dalam service:

* order harus dimiliki customer yang melakukan pembayaran
* order harus pending
* order belum expired
* order bukan cancelled/completed/paid
* payment harus tersedia
* payment.status harus unpaid/rejected atau pending jika memang digunakan
* payment method hanya bca, bri, qris
* nominal harus berasal dari order.total_price
* jangan menerima nominal dari frontend
* pembayaran yang sudah verified tidak boleh diproses lagi

Jika ownership sebelumnya hanya ada di PaymentController, pindahkan/duplikasi validasi yang diperlukan ke service agar direct service call juga aman.

Gunakan DB::transaction().
Lock order dan payment dengan tepat.

Hasil pembayaran berhasil:
payments.status = verified
payments.payment_method = bca/bri/qris
payments.amount = order.total_price
payments.transaction_id = transaction ID internal
payments.paid_at = now()
orders.order_status = paid

Jika orders.payment_status masih dipertahankan untuk compatibility:
orders.payment_status = verified

5. PAYMENT METHOD

Audit seluruh project untuk:
transfer
virtual_account
e_wallet
cash

Pastikan tidak ada lagi yang menjadi pilihan aktif.

Semua pilihan aktif harus:
bca
bri
qris

Sangat penting:
Periksa BookingService.

Pastikan BookingService TIDAK lagi membuat:

'payment_method' => 'transfer'

karena enum final hanya:
bca
bri
qris

Jika payment_method memang seharusnya dipilih saat pembayaran, gunakan pendekatan yang kompatibel dengan schema saat ini dan jangan membuat booking gagal karena enum.

6. INVALID STATE PROTECTION

Pastikan aplikasi tidak menghasilkan kombinasi:

pending + verified
paid + unpaid
paid + rejected
cancelled + verified
expired + verified
cancelled + pending payment
expired + pending payment

Jika ditemukan data inconsistent dari legacy fixture, jangan diam-diam menganggap valid.

Service harus menolak operasi yang akan menghasilkan kombinasi invalid.

Pastikan flow:

→ pending + unpaid

Untuk saat ini JANGAN hapus kolom.

13. DOUBLE PAYMENT / CONCURRENCY

Periksa apakah locking saat ini cukup untuk mencegah dua request pembayaran terhadap order yang sama.

Jika database/test environment sulit melakukan true concurrent test, minimal tambahkan test sequential double-submit dan dokumentasikan keterbatasan concurrency test.
